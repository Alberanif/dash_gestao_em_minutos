# PRD — Dash V2 (novo layout, piloto no Indicadores)

**Date:** 2026-10-22
**Status:** Approved (decisões validadas em entrevista com o owner)
**Owner:** Alberani

## 1. Contexto e problema

O dashboard atual funciona: banco, cálculos de métricas e coletas de dados (Hotmart, Meta Ads, YouTube, Instagram, leads) estão estáveis. O problema é a camada visual. Hoje o Indicadores é um painel técnico e plano, com tema escuro (`.dash-dark`), bordas de 1px, sem sombras, sem profundidade e sem movimento. O pedido do owner é uma **V2 com layout completamente novo**: responsivo, interativo, animado, focado em elementos visuais e com acabamento premium, sem pesar.

**Objetivo:** construir a V2 como uma nova camada visual sobre **toda** a estrutura existente (banco, migrations, cálculos, coletas, autenticação), começando por um piloto no Indicadores, para provar a linguagem visual, o desempenho e as animações antes de replicar para as demais áreas.

**Uso:** misto, com **desktop como alvo principal** (a partir de 1280 px) e celular para consulta rápida. Equipe interna pequena (a confirmar); a validação do piloto é feita só pelo owner.

## 2. Escopo

### Incluído

- **Design system V2** (tokens, fontes, primitivos de UI, biblioteca de gráficos, camada de movimento) isolado em `src/components/v2/`.
- **Shell V2** (navegação, layout responsivo) em `src/app/v2/`.
- **Piloto Indicadores V2** em `/v2/indicadores/...`: seletor de eventos e dashboard do evento, com herói em WebGL.
- **Extração estrutural da lógica** das rotas `/api/indicadores/*` para `src/lib/indicadores`, com as rotas passando a chamá-la e devolvendo o mesmo JSON.
- **Infra de qualidade**: orçamento de desempenho e bundle no CI, testes de paridade, Playwright.

### Fora de escopo

| Item | Motivo |
|---|---|
| Migrar as demais áreas (Ultimates, vendas, ajustes, LTV, social seller, EQA, agente) | Vêm em ondas depois do piloto estabilizado |
| Mudanças em banco, migrations, cálculos ou coletas | A V2 reaproveita tudo como está |
| Mudança visual ou funcional no V1 | O V1 fica intocado; só a extração estrutural das rotas o toca |
| Ligação do V1 para o V2 (botão, redirect, feature flag) | Decisão: acesso por URL `/v2/...`, validado só pelo owner. Aposentar o V1 do Indicadores é decisão futura |
| Remover o Recharts | Continua no V1 até ele ser desligado |
| Teste visual automático (snapshots) de tudo | Só depois que o piloto estabilizar |

## 3. Decisões de arquitetura (validadas em entrevista)

1. **Mesmo repositório, mesmo app Next.** A V2 vive em `src/app/v2/` e `src/components/v2/`. A pasta `dash_gestao_v2/` guarda só PRD, tokens e referências visuais. Uma regra de lint proíbe o V1 de importar de `v2/`. Um build, um deploy, e reuso direto de APIs, `src/lib` e sessão.
2. **HTML puro foi descartado.** A personalização e a responsividade vêm do CSS e dos tokens, não do HTML, e React entrega componentes, rotas e a autenticação Supabase SSR que o app já usa.
3. **Fatia vertical.** Primeiro design system e shell, depois o Indicadores como piloto, depois as outras áreas por ondas.
4. **Estética completamente nova** dentro do tema escuro, sem herdar o `.dash-dark`: sombras, feixes de luz, profundidade e elementos inéditos. Tokens próprios sob um root `.v2`, definidos num `@theme` do Tailwind 4. O `dash-theme.css` não é alterado. Fontes via `next/font` (self-host), sem `@import` do Google Fonts. A direção é estilo Linear/Vercel/Stripe como base, com doses de HUD apenas no herói do Indicadores.
5. **Movimento.** CSS e SVG como base, com Motion para orquestração, layout, gestos e números que contam. **Um único momento de WebGL** (OGL ou Three.js, carregado sob demanda) no herói do Indicadores, com fallback em CSS. Sem GSAP e sem WebGL nas demais telas.
6. **Gráficos** em visx sobre D3, com Motion, numa biblioteca interna pequena (linha e área, barras, funil, rosca, sparkline). Nenhum gráfico do projeto passa de 5 mil pontos, então SVG basta. O Recharts não entra no V2.
7. **Dados.** Estratégia híbrida: o servidor busca a primeira carga (período padrão) direto de `src/lib/indicadores` e envia por streaming com Suspense. Depois que o usuário mexe nos filtros, o cliente usa TanStack Query nas mesmas funções, expostas pelas rotas atuais. A lógica de cada rota de `/api/indicadores/*` é extraída para `src/lib/indicadores`, e rota e página V2 chamam a mesma função.
8. **Acesso.** Rota paralela `/v2/...`, sem ligação a partir do V1. Continua protegida pela mesma sessão e pelo `resolveAccountRole` (pendente vai para aguardando aprovação, comum vai para base de dados). Não é "aberta porque ninguém conhece a URL".
9. **Estilo e componentes.** Tailwind 4 mais primitivos headless do Radix (dropdown, dialog, popover, tooltip, tabs, select) para acessibilidade. Sem shadcn, que tem visual reconhecível. Os componentes ficam em `src/components/v2/ui`.

## 4. Requisitos não funcionais (orçamento de desempenho)

| Métrica | Meta |
|---|---|
| LCP | Menos de 2 s no desktop e menos de 3 s no celular em 4G |
| Skeleton visível | Em menos de 500 ms |
| INP | Menos de 200 ms; trocar filtro responde na hora e anima |
| Animação | 60 fps no desktop; 30 fps no mínimo em celular de gama média; animar só `transform` e `opacity` |
| JS inicial | No máximo 180 KB gzip por rota, sem contar o chunk do WebGL |
| WebGL | Carrega sob demanda após o primeiro conteúdo; fallback em CSS em dispositivo fraco, com `prefers-reduced-motion` ou aba oculta; pausa fora da tela |
| Responsividade | Desktop desenhado primeiro, a partir de 1280 px; reorganiza por container queries até 360 px, sem rolagem horizontal; celular prioriza consulta rápida |
| Acessibilidade | Foco visível por teclado, contraste adequado, `prefers-reduced-motion` respeitado |
| Se o JS estourar | O primeiro corte é o Supabase client no navegador, já que o servidor busca a primeira carga |

## 5. Estratégia de testes

1. **Paridade de dados (a mais crítica).** Para cada função extraída das rotas, um teste compara o resultado novo com o que a rota entregava antes, com as mesmas entradas. Teste novo só vale com prova de mutação (quebrar a lógica de propósito e confirmar que falha). O Jest do projeto só transpila, então a guarda de tipos é o `tsc`.
2. **Qualidade de código.** `tsc --noEmit` e lint no CI, regra que proíbe o V1 de importar de `v2/`, e o orçamento de bundle como verificação automática.
3. **Visual e interação.** Playwright em 1440 px e 390 px nos estados principais (carregado, vazio, erro, filtro aplicado). O herói WebGL não tem captura de referência; só se verifica que o fallback entra quando deve. Teste manual de teclado e `prefers-reduced-motion`. Snapshots visuais só depois que o piloto estabilizar.

## 7. Riscos e pontos de atenção

- **JS inicial de 180 KB** é apertado com React, Next, Motion e visx. Mitigação: orçamento medido no CI desde a issue 7 e o corte descrito na seção 4.
- **Extração das rotas** toca o V1. Mitigação: teste de paridade por função, rotas devolvendo o mesmo JSON.
- **Fundo escuro com efeitos de luz** cansa em uso diário se espalhado. Mitigação: o WebGL fica só no herói do Indicadores e o resto segue o estilo contido.
- **Referência visual concreta** ainda não existe (só a direção da seção 3, item 4). A direção definitiva de tipografia e paleta é definida na etapa de design, antes das issues 8 a 10.
- **Sessões concorrentes** podem trocar a branch do diretório; conferir `git status -sb` antes de commitar.

## 8. Entrega

- Uma branch e um PR por issue filha, a partir da `main`, cada PR referenciando sua issue.
- Nenhuma migração de banco, nenhuma variável de ambiente nova.
- Dependências novas previstas: `motion`, `@visx/*`, `@tanstack/react-query`, `@radix-ui/*`, OGL ou Three.js, Playwright (dev).
